# LittleKedi Expansion

An inference-only experiment that expands a small language model with a new residual MLP immediately before its tied LM head.

The project compares three checkpoints:

- **A** — the original `LittleKedi-tiny-base` model, 1,990,912 parameters.
- **B** — a random-control expansion, 2,990,770 parameters.
- **C** — an external-LLM-designed expansion, 2,990,770 parameters.

Both expanded checkpoints add exactly **999,858 new parameters** and keep every original base weight bit-identical. No fine-tuning, gradients, or optimizer are used.

The short version: **the expansion is mechanically correct, but it is a net cost on this benchmark suite.** The LLM-designed initialization preserves perplexity and memory much better than the random control, but neither variant improves accuracy over the original.

Full results are in [`results.md`](results.md). Machine-readable results are under [`results/`](results/).

## What Was Built

The base model is a 4-layer DeepSeek-style MoE language model:

- `dim=128`
- `vocab_size=8192`
- `max_seq_len=1024`
- tied input/output embeddings
- no separate LM head
- MLA attention
- one dense SwiGLU layer followed by three MoE layers

The new layer is inserted after the final RMSNorm and before the tied LM head:

```python
hn = self.norm(h)
y = hn + self.pre_head(hn)
logits = F.linear(y, self.embed.weight)
```

`pre_head` is:

```text
w1: [3890, 128]
b1: [3890]
w2: [128, 3890]
b2: [128]
forward: w2 @ gelu(w1 @ x + b1) + b2
```

Parameter count:

```text
w1: 497,920
b1:   3,890
w2: 497,920
b2:     128
total: 999,858
```

The original base checkpoint is never modified.

## The Three Checkpoints

### A — original

The released `LittleKedi-tiny-base` checkpoint, used as the reference.

### B — random control

The new layer is initialized with independent iid Gaussian weights:

```text
w1, w2 ~ Normal(0, 0.02)
b1, b2 = 0
seed = 0
```

This tests whether an arbitrary extra layer changes behavior, without any structure or design.

### C — external-LLM-designed

The new layer is generated by a deterministic script authored by an external LLM:

```text
Q = reduced QR of a seeded Gaussian matrix
w1 = Q
w2 = 0.15 * Q^T
b1 = 0
b2 = 0
```

`Q` has orthonormal columns, so the linear part of the branch is a scaled identity and GELU supplies a controlled nonlinear residual. The branch is intentionally modest: at input RMS 3.2, its output RMS is about 0.24.

The generator was frozen before any evaluation. Its hash is recorded in the checkpoint manifest and in [`results/construction_summary.json`](results/construction_summary.json).

## Quick Start

### Requirements

Python 3.10–3.12. Install dependencies:

```bash
python3 -m pip install -r requirements.txt
```

Tested with CPU-only `torch 2.14.1+cpu`, `tokenizers 0.23.3`, `safetensors 0.8.0`, `pyarrow 24.0.0`, `tqdm 4.67.3`, `requests 2.32.4`, and `psutil 7.2.2`.

### Evaluate the included B and C checkpoints

The original A checkpoint is not redistributed here. To evaluate A, provide a directory containing the original `config.json`, `model.safetensors`, and `tokenizer.json`.

```bash
export MODEL_DIR=/path/to/LittleKedi-tiny-base

python3 src/evaluate.py \
  --model-dir "$MODEL_DIR" \
  --models A B C \
  --batch-size 16 \
  --out-dir results
```

This writes per-stage JSON files and `results/summary.json`.

### Evaluate only the expanded checkpoints

```bash
python3 src/evaluate.py \
  --models B C \
  --batch-size 16 \
  --out-dir results
```

### Reproduce construction

Build B:

```bash
python3 src/make_checkpoints.py \
  --model-dir "$MODEL_DIR" \
  --mode random \
  --out checkpoints/random_seed0 \
  --seed 0
```

Build C:

```bash
python3 src/make_checkpoints.py \
  --model-dir "$MODEL_DIR" \
  --mode llm \
  --generator src/llm_generator.py \
  --out checkpoints/llm_generated \
  --seed 0 \
  --llm-model "external-LLM-authored" \
  --llm-prompt-sha256 "$(sha256sum src/llm_generator_prompt.txt | cut -d' ' -f1)"
```

Verify construction:

```bash
python3 src/verify.py \
  --model-dir "$MODEL_DIR" \
  --random-dir checkpoints/random_seed0 \
  --llm-dir checkpoints/llm_generated \
  --out results/verification.json
```

Run the full construction audit:

```bash
python3 src/finalize_construction.py \
  --model-dir "$MODEL_DIR" \
  --random-dir checkpoints/random_seed0 \
  --llm-dir checkpoints/llm_generated \
  --out results/construction_summary.json
```

### Rebuild frozen evaluation data

The processed evaluation files are included. To rebuild them from pinned dataset revisions:

```bash
python3 src/freeze_data.py \
  --model-dir "$MODEL_DIR" \
  --out-dir data \
  --seed 0
```

Raw downloads go to `data/raw/`, which is git-ignored. Dataset revisions and file hashes are recorded in `data/manifest.json`.

## Evaluation Protocol

### Accuracy

| Task | Items | Split |
|---|---:|---|
| SciQ | 1,000 | full test |
| ARC-Easy | 2,376 | full test |
| HellaSwag | 1,000 | fixed seeded subset |
| PIQA | 500 | fixed seeded subset |
| ArithMark-3 | 500 | fixed seeded subset |

All models use the same frozen examples, tokenizer, dtype, device, and code path.

Reported metrics:

- `acc`: raw choice log-probability.
- `acc_norm`: log-probability normalized by character length.
- `acc_norm_tok`: log-probability normalized by token length.
- `stderr`: binomial standard error of `acc_norm`.

### Perplexity

- WikiText-2 raw test.
- Non-overlapping 1024-token windows.
- 349 windows, 357,027 scored tokens.
- Reports token perplexity and bits-per-byte.

### Latency

- CPU, batch size 1, 4 threads.
- Prefill lengths: 128, 512, 1024.
- 20 repetitions after 3 warmups.
- Decode: 64 cached steps after a 128-token prefill.
- Median wall-clock time is reported.

### Memory

- Each model runs in a separate process.
- Parameter bytes, state bytes, baseline RSS, peak RSS, and inference delta RSS are recorded.
- Peak RSS is process-level and allocator-dependent.

## Construction Verification

The full audit passes **70/70 checks**:

- original model hash unchanged
- B and C have exactly 2,990,770 parameters
- B and C have exactly 999,858 new parameters
- all original base tensors are bit-identical
- extra keys are exactly `pre_head.w1`, `pre_head.b1`, `pre_head.w2`, `pre_head.b2`
- zeroing `w2` and `b2` restores original logits within `1e-6`
- the new layer is called once in normal and cached forward paths

- B reproduces exactly from seed 0

## Findings

1. **The construction is valid and reproducible.** The new layer is connected correctly, the base model is unchanged, and C is deterministic.
2. **C is the safer expansion.** It raises perplexity by 1.9% vs 5.8% for B, and has lower peak RSS in this run.
3. **No accuracy gain.** C does not beat A on `acc_norm` for any task. B beats A only slightly on HellaSwag and ArithMark.
4. **B vs C is mixed.** B is better on 4 of 5 `acc_norm` tasks; C is better on PIQA. The gaps are small relative to standard errors.
5. **The extra capacity is expensive.** The expanded models add ~1M active parameters, 14–45% prefill latency, ~24% decode latency, and 1.9–5.8% perplexity. That cost is not offset by accuracy on this suite.

**Bottom line:** an LLM-designed, structured initialization preserves the base model much better than a random control, but it does not produce a capability gain. The pre-head layer is not justified for accuracy on these benchmarks without further work.

## Limitations

- CPU-only, single run, 4 threads; latency and RSS measurements are noisy.
- HellaSwag, PIQA, and ArithMark-3 use fixed subsets, not full validation sets.
- Accuracy deltas are mostly within one standard error.
- Peak RSS is allocator-dependent.
- The tokenizer is the released byte-level BPE tokenizer as-is; it does not split digits.
- This is initialization-only expansion. No training or adaptation was attempted.
- Results may not generalize to other models, tasks, seeds, or hardware.
